A guide for your getAudioData work

Understanding audio
before you write the player

You already know how to give compressed video to VideoDecoder and receive pictures. Audio starts the same way. The main difference is what comes out: a sequence of numbers that must play continuously.

We'll use AAC-LC, the audio format your codec parser currently accepts. You don't need to learn how audio compression works internally. You need to understand the input, the output, and how to keep sound playing.

For the missing audio in your test files, start with the lacing lesson.

1. Where does getAudioData fit?

Your getVideoData reads the MKV file and yields compressed video packets. A packet is a piece of compressed media ready for the decoder. The function doesn't produce a VideoFrame; the decoder does that later.

The same separation applies to audio:

Read the fileYour MKV reader extracts compressed audio packets.
Decode the packetsAudioDecoder produces numbers that describe the sound.
Play the soundWeb Audio sends those numbers to the speakers at the right time.

Reading one track out of a container is called demuxing. That is the job your function does. WebCodecs handles decoding. Web Audio handles playback. These APIs work together, but none does all three jobs for you.

This explains a common surprise: AudioDecoder can decode successfully while the page stays silent. Its output still needs somewhere to go, just as a decoded video frame still needs to be drawn.

2. What does decoded audio contain?

Imagine measuring a sound signal thousands of times each second. Each measurement is a sample. Decoded audio is a long sequence of these numbers, often called PCM. A zero value means silence at that instant.

Stereo has two channels: left and right. At each instant, there is one sample for each channel. That pair is one sample frame. This use of “frame” is different from a whole picture in video.

Time:        first    second    third
Left:         0.1      0.2       0.3
Right:       -0.1     -0.2      -0.3

3 sample frames, 2 channels, 6 numbers

The sample rate tells you how many frames make one second. At 48,000 Hz, each channel has 48,000 samples per second. A block of 960 frames therefore lasts:

960 / 48,000 = 0.020 seconds = 20 milliseconds

The number of channels does not change that duration. Six channels give you more numbers at each instant, not more time.

Try changing the channel count
21.333 ms2,048 numbers · 8,192 bytes as float32 samples

The numbers can be arranged in two ways. Interleaved stereo stores L0, R0, L1, R1. Planar stereo stores all the left samples together and all the right samples together. The sound is the same; only the memory arrangement changes.

3. Lacing: one block, many packets

Lacing puts several compressed packets in one MKV block. They share a header to save space. Your reader must find each packet before it gives the bytes to AudioDecoder.

No lacing: header | packet A
Lacing:    header | count | size information | A | B | C

Here, a packet means a compressed AAC frame. It can decode into 1024 sample frames per channel. These are two different uses of “frame.”

What happened in your file: the first cluster of Fate Strange Fake – 08 contained 87 audio packets in 11 laced blocks. Your if (lacing !== 0) return null skipped all of them. A shorter playback timer cannot recover those packets.

Read the mode, then the count

Your existing expression extracts the lacing mode from the block's flags:

const lacing = (flagsByte & 0x06) >> 1;
ValueModeHow to find packet sizes
0NoneOne packet. All bytes after the flags belong to it.
1XiphAdd size bytes. Explained below.
2Fixed-sizeDivide the remaining packet bytes equally.
3EBMLRead the first size, then changes from the previous size.

For modes 1–3, the byte after the flags stores packet count minus one. A value of 7 means eight packets. Read this as an ordinary byte, not a VINT. Mode 0 has no count byte.

The same rules apply to SimpleBlock and the Block inside a BlockGroup. Read each block's mode; it can change within a track.

Read one EBML example by hand

Your two test files use EBML lacing. Start here. This made-up example has three packets, with lengths of 300, 298, and 301 bytes. Only the header bytes are shown; it is not playable AAC.

82 00 00 86 | 02 | 41 2C | BD | [A: 300] [B: 298] [C: 301]
block header count size A  change       packet bytes

The header says track 2, relative timestamp 0, and flags 0x86. Those flags give lacing mode 3. The header is four bytes here because the track number uses one byte. Your code must still use the actual track-number width.

  1. Count: 02 means 2 + 1 = 3 packets.
  2. First size: 41 2C is an unsigned VINT with value 300.
  3. Next size: BD stores a signed difference of −2. Packet B is 300 − 2 = 298 bytes.
  4. Last size: no size is stored for C. After the count and size information, 899 bytes remain. C gets 899 − 300 − 298 = 301.

For N packets, EBML stores one first size and N − 2 differences. With two packets, there are no differences to read.

How do those VINT bytes become numbers?

A VINT is an integer whose first set bit tells you its byte width. A leading 1 means one byte; 01 means two. Remove that marker bit to get the number.

41 2C = 01000001 00101100
        remove the 01 marker prefix
        remaining value = 1 × 256 + 44 = 300

BD    = 10111101
        remove the leading 1
        remaining value = 61

A size difference then needs one more step. Subtract 2 ** (7 * width - 1) - 1, where width is the VINT's byte count. For one byte, subtract 63. Thus 61 − 63 = −2. For two bytes, subtract 8191.

Your block timestamp uses a different signed-number format. Its 16-bit conversion will not work for these differences.

One trap in your parseSizeAt helper

That helper turns an all-ones value into −1 for an unknown element size. Lacing values do not use that rule. For example, FF has VINT value 127 and means a one-byte difference of 127 − 63 = +64. Reuse the VINT byte-reading logic, but keep the element-size rule separate.

Turn the sizes into byte ranges

In this example, packet A starts eight bytes after b.dataStart: four header bytes, one count byte, two size bytes, and one difference byte.

Offsets relative to b.dataStart; the end is excluded:

A: [  8, 308)   → 300 bytes
B: [308, 606)   → 298 bytes
C: [606, 907)   → 301 bytes

Only these three ranges go to the decoder, one packet per chunk. The count and size bytes describe the packets; they are not audio. They are also not child elements for peekElementAt to parse.

How do fixed-size and Xiph lacing differ?

Fixed-size: after the count byte, 900 bytes remain for three packets. Each gets 900 / 3 = 300 bytes. If the division has a remainder, reject the block.

Xiph: for each packet except the last, add bytes until you read one below 255. For a size of 300, read FF 2D: 255 + 45. For exactly 255, read FF 00; the zero ends that size. The last packet gets the remaining bytes.

Each packet also needs its own timestamp

The block timestamp belongs to packet A. B follows A, and C follows B, with no gaps. For your supported AAC-LC configuration, use framesPerPacket / sampleRate for the packet duration. Compressed byte size does not tell you duration.

Example: 1024 frames / 44,100 Hz ≈ 0.023220 seconds

If A starts at 2 seconds:
A: 2,000,000 microseconds
B: 2,023,220 microseconds
C: 2,046,440 microseconds

These values are rounded for display. Calculate each offset from its packet index and the exact duration, then round for WebCodecs. Do not repeatedly add a rounded duration.

4. What changes when you use AudioDecoder?

The pattern will feel familiar: create a decoder with output and error callbacks, configure it, then submit compressed chunks. Audio needs a different configuration and produces a different output object.

Describe the audio format

The configuration includes a codec string, sample rate, channel count, and sometimes extra binary data called description. “Description” does not mean a text label. It contains information the codec needs to interpret the compressed bytes.

For your AAC track, that data is called AudioSpecificConfig. Your existing codec parser reads it. In WebCodecs, supplying it means the decoder expects raw AAC packets. Without it, the AAC registration expects packets with ADTS headers, a different format. “Raw AAC” is still compressed; here, “raw” means it has no ADTS header.

Check the exact configuration with AudioDecoder.isConfigSupported(). Having the API in the browser does not guarantee support for every codec. For AAC, the encoded configuration determines the actual rate and channels; the generic API still requires those fields.

Give each chunk the correct timing and type

An EncodedAudioChunk carries compressed bytes, a timestamp, a type, and an optional duration. WebCodecs measures timestamps and durations in microseconds: one second is 1,000,000 microseconds.

The AAC specification says its chunk type is "key". This is why copying the video keyframe logic without checking the audio rules can be misleading. Read the codec's rule before deciding what your generator should yield.

Wait for output through the callback

decode() submits work and returns. The output callback later receives an AudioData object. Adding await to decode() does not wait for that output. Nor should your code depend on every call immediately producing exactly one object.

At the end of a finite input, flush() waits for pending decoding and output. It does not wait for the sound to finish playing. Errors can arrive through the error callback too, after the call that submitted the packet.

5. How do those numbers become sound?

Read the properties of each AudioData: its sample rate, channel count, frame count, sample format, and timestamp. These describe the output you actually received.

Web Audio stores samples in an AudioBuffer, with one float32 array per channel. Each float32 number uses four bytes. An AudioBufferSourceNode reads that buffer and plays it through connected audio nodes. Connecting it to the context's destination gives the sound a route to the speakers.

To move samples out of AudioData, learn copyTo(). It can convert them to f32-planar: floating-point numbers, separated by channel. This fits Web Audio's storage format.

Once you have copied everything you need, call close() on the AudioData. That releases its media resource. Your separate copy remains usable. Keeping every decoded object forever would keep using more memory.

Keep the sample rate attached to the samples correct. If 44,100 frames represent one second, labelling them as 48,000 Hz makes them play too fast. Web Audio can convert between a buffer's rate and the context's rate; changing the label yourself is not that conversion.

A source node can start only once. Also, the browser may keep the audio context suspended until the user clicks Play. Check the context state if decoded samples arrive but you hear nothing.

6. How do you keep it playing smoothly?

Your video loop can wait until a frame is due, then draw it. Audio needs an uninterrupted sequence of samples. Starting each small block when a JavaScript callback happens to run can leave gaps.

Instead, Web Audio lets you schedule sound ahead of time. Its clock is AudioContext.currentTime, measured in seconds. That clock starts with the context, not with your movie.

Suppose you decide that movie time 3.000 seconds will play at audio-context time 12.100 seconds. Sound belonging at movie time 3.040 must then start at context time 12.140. You keep the same 40-millisecond difference:

Movie time:          3.000 s    3.020 s    3.040 s
Audio-context time: 12.100 s   12.120 s   12.140 s

Convert WebCodecs microseconds to seconds before comparing these values. Preserve the timestamps shared by audio and video; setting each track's first timestamp to zero independently can destroy their intended timing difference.

Keep some audio ready, but not the whole movie

A queue of decoded samples covers short delays in reading or decoding. Measure it in seconds as well as objects. Ten 20-millisecond blocks give you 0.2 seconds of sound. Ten 100-millisecond blocks give you a full second.

decodeQueueSize measures pending decoder requests. It does not tell you how much decoded sound is ready. Watch both, because many requests can be submitted before their output callbacks run.

Finally, avoid repeatedly rounding durations. At 48,000 Hz, 1024 frames last about 21.333 milliseconds. Treating every block as exactly 21 milliseconds gradually loses time.

7. What should you try before the full player?

  1. Understand one sample block. Given 1024 frames at 48,000 Hz, calculate its duration. Then explain why stereo doubles the number of values but not the time.
  2. Make sound without MKV. Create a short test sound with Web Audio. Start it from a button. This lets you learn playback without wondering whether your packet reader is broken.
  3. Decode a small, known input. Use valid AAC packets and matching configuration. Log the output's frame count, rate, channels, format, and timestamp. Copy some samples, then release the output.
  4. Check one laced block. Work through the packet-range exercise. Confirm that each range contains one packet and that the final range ends at the block's end.

Before you call the player complete, handle normal end-of-file separately from damaged input. On Stop, release queued samples and stop sound already scheduled. On seek, prevent old reads and old samples from entering the new playback position.

You can leave AudioWorklet, shared memory, and compression mathematics for later. Exact seeking and gapless playback need more study of codec delay and padding, but they don't need to obscure your first lesson.
